# T4: reopen a confirmed page, engine half (3 Nov 2026)

**Status:** done, on `scriba-mvp`. Track B work, run in `scriba/` since the trust fixes run one at a time. 849 tests (7 new), typecheck, lint and build pass. No live calls, nothing spent. The migration is **not yet on the hosted dev project**: `supabase db push --dry-run` shows it is the only one pending, and it waits for the user's go-ahead.

## What changed

### Migration `supabase/migrations/20261103120000_scriba_reopen.sql` (additive)

- **A new audit action, `reopen`.** The `review_events` action check allows it. The audit trigger now writes `reopen` for confirmed → draft. Rejected → draft is still `restore`.
- **`scriba_reopen_preview(p_owner_id, p_run_id)`**: what reopening would do, changing nothing. It returns:
  - `latest`: whether this run is the page's latest succeeded reading;
  - `record_ids`: the page's records in the khata, from any of its readings;
  - `business_date`;
  - `closed_days`: the closed days that hold the page. That's its own day, or a close whose `record_ids` name one of its records (a page whose date was moved after the close).
- **`scriba_reopen_page(p_owner_id, p_run_id)`**, all or nothing:
  1. Checks that the run is a succeeded reading of this owner.
  2. Locks every line of the page, of every reading.
  3. Takes the checks from the preview: the run must be the latest reading, and the page must have records.
  4. Applies the loop limit (below).
  5. Deletes the page's `confirmed_records` and sets its confirmed lines back to `draft`. The trigger writes one `reopen` event per line.
  6. Sets the page back to `extracted`.
  7. Writes one page-level event (`entry_review_id` null, action `reopen`):
     - `previous_values`: `{ status, records }`, where `records` holds every record that left, whole (`to_jsonb` of the row: id, run, type, amounts, party, texts, confirmation id);
     - `new_values`: `{ status: "extracted", lines, closed_days }`.
  8. Returns `{ records, lines, business_date, closed_days }`.
- **What stays:**
  - the lines' values and his answers (`page_reviews`);
  - the confirmation's validation findings, as history;
  - the parties;
  - a closed day's close, untouched.
- **Errors:**
  - `P0002`: not his succeeded reading;
  - `55000` with hint `not_latest` or `not_confirmed`;
  - `53400` with hint `busy`: the loop limit.
- Both functions are for the service role only (revoked from `public`, `anon` and `authenticated`).
- A partial index `review_events_page_reopens` backs the limit's count.

### API `src/app/api/runs/[id]/reopen/route.ts`

- **The owner is checked through his own client first** (the run must be his and succeeded, else 404). Then the service role calls the function, which checks the owner again. This is how confirm does it.
- **`GET`**: the preview, so the app can warn before he taps. It changes nothing. It returns `{ canReopen, reason, records, businessDate, closedDays, dayClosed }`, where `reason` is `not_latest`, `not_confirmed` or null.
- **`POST`**: the reopen. It returns `{ reopened, lines, businessDate, closedDays, dayClosed }`. Refusals:
  - 404: not his succeeded reading;
  - 409 `not_latest`: "This page was read again since…";
  - 409 `not_confirmed`: "…nothing in the khata to reopen";
  - 429 `busy`: the loop limit;
  - 500: "Nothing was changed".
- No request body.

## Tests (`tests/db/rls.test.ts`, "reopen a confirmed page (T4)", pglite)

- **Reopen:**
  - the preview is right and changes nothing;
  - after the reopen, the page's records are gone, all lines are drafts and the page is `extracted`;
  - each line has `confirm` then `reopen` (confirmed → draft);
  - the page event holds the records as they were (id, run, type, amount, party), and its `new_values` are right;
  - the confirmation's finding and the party stay;
  - he can edit the lines again (RLS);
  - another page's records and status are untouched.
- **Confirm again:** three new records with new ids, and the page is `confirmed`.
- **Refused:**
  - another owner, for both functions;
  - a page never confirmed;
  - an older reading once the page was read again.
- **The newer reading:** reopening from it takes out the records the older one put in (the event names the older run), and the newer reading can then be confirmed.
- **A closed day:** closes on its own day and on a day whose `record_ids` name one of its records. Preview and reopen both list `["2026-11-01", "2026-11-02"]`, and the close's `record_ids` are unchanged.
- **Users can't call** either function.
- **Rejected → draft** is still `restore`.
- **The loop limit:** with 30 page reopens in the hour it refuses, and the records stay.

## Decisions I made (technical)

- **Named `scriba_reopen_page`, not `scriba_reopen_run`, and it reopens the whole page.** Every record of the page leaves, whichever reading put it in, and the run given must be the page's latest reading. This follows the confirm route's rule that a page counts from one reading only. Without it, a page read again after confirming could never be fixed: the new reading would be refused as `page_already_confirmed`, and the old one isn't shown.
- **A preview, with `GET`.** T5's confirm sheet must warn about a closed day *before* he taps, and the plan's POST only reports it after. The preview is a SQL function the reopen itself calls, so the warning and the rule can't drift apart.
- **"Closed day" covers both cases:** the page's own day, or a close that names one of its records. A close's `record_ids` are its snapshot, so a page whose date moved after the close is still caught. The API gives the days (`closedDays`), not only a flag.
- **Lock the lines first, then read.** A confirmation running at the same time either finishes first (and its records leave too) or waits. Locking the page row instead could let a confirmation slip records in, or deadlock against confirm, which locks lines then updates the page.
- **The loop limit lives in the database:** 30 page reopens per owner per hour, counted from the audit trail. Confirm has no limit, so "rate-limited like confirm" meant none. But a reopen deletes records, and an in-memory limiter (like `/api/ask`'s) doesn't hold across serverless instances. A shopkeeper fixing pages never comes near 30.
- **The page goes back to `extracted`**, even if it was `partially_confirmed`. With no records left, nothing of it is in the khata.
