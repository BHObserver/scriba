# Scriba implementation plan

Living plan for the hackathon build. Status is updated as work lands; only items
that were actually run are marked done.

- **Submission deadline:** Wed 4 Nov 2026, 9:00 PM EST (= Thu 5 Nov, 08:00 Bangladesh time). US daylight saving ends on 1 Nov, so the deadline is in EST (UTC−5).
- **Building period:** 27 Oct – 4 Nov 2026. All code in this repository was written in that period. The Git history starts on 29 Oct.

## Decisions taken

| Topic | Decision | Why |
|---|---|---|
| Bun vs Node ("the Bun split") | **Bun** is the package manager, script runner and test runner (`bun install`, `bun run`, `bun test`). **Next.js runs on Node.js** for `dev`, `build` and Vercel. One app, no workspaces. | Bun is fast for installs and tests. Next.js and Vercel officially target Node, and Cache Components requires the Node runtime. Splitting into packages would add ceremony with no benefit for one app. |
| Gemini sample | Reference only. Scriba is written from scratch. The sample is git-ignored so judges never see non-Meta code. | It proved that "image + JSON prompt → Bangla transcription" works. Its client-side resizing, automatic retries and fake fallback results are the opposite of what Scriba needs. |
| Meta endpoint | `POST https://api.meta.ai/v1/responses` through the official OpenAI-compatible SDK. Strict JSON Schema in `text.format`, `reasoning.effort: low`, `max_output_tokens: 8000`, `store: false`, SDK retries disabled. | Documented in dev.meta.ai docs (image understanding, structured output, reasoning). `store: false` keeps responses from being retained. The strict schema with `type: ["string","null"]` was accepted live. |
| Model | **`muse-wonder-1.0`** at `effort: low` (standard mode), since 30 Oct. Before that `muse-spark-1.3`. Contributor mode is never selected automatically. | Live comparison on S01–S04, 30 Oct (table in `docs/HANDOFF.md`): Wonder read S01–S03 perfectly in all four of its runs and got 36–38 of 40 numbers right with prompt 3. Spark at low effort scored 32–35, varied between identical runs, and invented self-consistent lines (`২ × ১৪০ = ২৮০` for `১ × ১৪০ = ১৪০`) that pass every check. Medium or high effort on Spark didn't close the gap. Wonder costs ≈ $0.06 per image against ≈ $0.017. Muse Wonder is on the hackathon's list of eligible models. Standard-mode content is not used for training. |
| Image preparation | Photos under 3.3 megapixels are upscaled (lanczos3) to about 3.3 MP before sending; larger ones go as uploaded. The cache key version was bumped to `scriba-cache-2`. | Meta resizes images itself. Measured with `/v1/responses/input_tokens`: a 958×1280 WhatsApp photo reaches the model as 1,777 tokens, and the count rises to a cap of 4,263 at about 3.3 MP. Upscaling took Spark from 28 to 30 of 30 on S01–S03. It adds about $0.01 per image on Wonder. |
| Prompt `scriba-prompt-3` | Adds a "Reading digits" section. Read each digit from the ink and never use arithmetic to choose a digit. Bangla ৪ and ৭ look like Latin 8 and 9, so on a Bangla page those shapes are read as ৪ and ৭ and written as Bangla digits. ১/২/৯ and ৩/৬ are easily confused, so unsure fields go in `review`. | Prompt 2 told the model to keep the digit style. Writers mix scripts, and `8` meaning ৪ was misread as eight. The model also "fixed" misread lines by calculating, for example `৬ × ৬০ = ৩৬০` when the ink says `৩ × ৬০ = ১৮০`. Wonder on S04 went from 5–6 to 6–8 of 10. |
| Numbers | The model copies numbers **as written**. TypeScript normalizes Bangla and Arabic digits to integer poisha. | The model reads; it does not compute. Deterministic code does the arithmetic, which keeps "AI proposes, code verifies" true. |
| Line positions | Requested in the same single call (bounding boxes on Meta's 0–1000 grid), validated, and shown only as "the model's estimate". | Meta's perception grounding comes at no extra request cost. It's an honest use of a distinctive capability. |
| Upload path | Browser → private Supabase bucket under the user's own folder (Storage RLS). The server then re-downloads, inspects and checksums the bytes before recording anything. | Vercel functions cap request bodies at 4.5 MB, and the upload limit is 8 MB. The original is never proxied or re-encoded. |
| Trust model | Users read their own rows; they can write only what they author (review edits, ground truth). Extraction results, usage, confirmations and evaluations are written by the server with the secret key, after verifying the user. | Prevents a user from forging "successful" runs or confirmations through the Data API. |
| Output budget | `SCRIBA_MAX_OUTPUT_TOKENS=8000` (was 1,800). | Live, 29 Oct: at `effort: low` the first call spent 1,798 of 1,800 tokens on reasoning and returned nothing (`incomplete`). Snippets then used 1,255–2,752 output tokens, 675–1,898 of them reasoning. Reasoning can't be switched off on `muse-spark-1.3` (`none` returns 400), and only tokens used are billed, so a high ceiling costs nothing extra. Worst case ≈ $0.04 per image. |
| Prompt `scriba-prompt-2` | Header lines (date, customer, "Sample-0X" labels) are page fields, not entries. Opening and closing balance figures go in `amount`. `মোট বাকিতে` / `আজকের বাকি` are subtotals. | Prompt 1 made the header lines `unknown` entries and put the balance figures under `balance`, so the opening → closing check couldn't run. The parser also moves a balance-only figure into `amount` on opening and closing lines, as a deterministic safety net. |
| Orientation | The user can turn the photo before analysis. Modes `rotate_90/180/270` send a server-rotated copy (sharp, after the checksum check); the stored original never changes. The review shows the photo in the same orientation, so the line boxes line up. | Live, 29 Oct: sideways S03 came back with line 2 misread and the total misread to match it, so **every check passed on wrong data**. The same photo upright was read perfectly, with a third of the reasoning tokens. Asking the model to detect orientation would cost a call; a manual turn is deterministic. |
| Voice correction (Muse Voice Transcribe) | **Built in P1 (1 Nov)**, as master plan session P1: "বলে দিন" in the fix sheet → 24 kHz mono PCM16 WAV → `/api/voice` → `/v1/asr/transcribe` (push-to-talk, `languageBias: ["Bengali"]`, plus English on the English screen) → deterministic Bangla number-word reader → number placed in the field, never saved until "keep". See `docs/sessions/P1.md`. | Track A had finished early, and F1 is blocked on production credentials. Voice is cheap (≈ $0.0005 a clip), and the parser carries the risk, so it's fully tested. |
| Blocks storage (U1, 2 Nov) | **No migration.** Blocks live in JSON columns that already exist: the reading in `extraction_runs.result`, the editable blocks in `page_reviews.page_values`, each line's block in `entry_reviews.entry_values`. Confirmation links the block's party through the existing `party_id`. The page and line edit routes keep stored blocks when an older client sends values without them. | The hosted project is also production (F1), so a table now needs a go-ahead and a matching deploy, and it would freeze a shape U2 and B7 haven't used yet. The money screens need only `party_id`. If the party ledger must show the rep per record, add `confirmed_records.person` in one additive migration (B7 or later). |
| Goods without a price (U1) | A goods line is an entry with item, qty and unit and **no amount**. It's priced **per line** (its amount is filled in later, by him or from a memo in U4). It can't be confirmed until then: the existing rule "a missing amount cannot be approved as zero" applies, and `confirmed_records.amount_poisha` is `not null`. The block's balance check is `unverifiable` with reason `unpriced_goods` and gives the known part ("৳1,300 so far"). | One record per line keeps item history and the qty × rate check. A delivery total for the whole block is U2's to design; it must not confirm the item lines as money (see "Delivery total"). |
| Answers to Scriba's questions (U2, 2 Nov) | **No migration.** Questions are recomputed from the review state (`src/lib/questions/engine.ts`), so they never go stale in storage. An answer becomes ordinary review edits: line values, checked fields, a rejected or added line, the page date, a block's kind or party. The server works these out from its own copy of the question, never from the client. They're written through `entry_reviews` and `page_reviews` with version checks, so the existing triggers audit them. The answer itself is recorded in `page_values.answers` (question id, fingerprint of what it was about, option, accepted problems, time): the latest per question, at most 300. | The audit trail needs no new table, and "that's right" answers that change nothing are still recorded (as a `page_edit`). A recorded answer only hides its question while the fingerprint matches, like an acknowledgement, so a changed value is asked about again. Writes aren't one transaction (that needs an RPC, so a migration). A half-saved answer leaves complete, audited edits, and its question is asked again. |
| Delivery total (U2) | Two or more unpriced goods of one kind in a company block get one question: "what did they cost in all?" A total **adds one line** for the delivery (its type, the items joined, every source text joined with " + ") and **rejects** the unpriced lines it replaces. He can choose "I'll price each one" instead, which asks per line. | It's priced the way a memo is, and approval rules stay unchanged: every confirmed line has its own amount, and nothing is counted twice or as zero. The item lines stay in the review and audit trail. Per-item quantities survive only as text in the delivery line; U4 (memo) prices per item when a memo is photographed. |
| Question copy (U2b, 2 Nov) | D5's wording lives in the engine's `q.*` keys. The engine's question kinds, ids, options and fingerprints are unchanged. A question also has a `why` (a sentence plus `verified`, which means code checked it against his records and the screen shows a tick), and an option may have a `detail` ("6 at ৳15 each"). The figures in a sentence come from the lines as read, and code does any sum. `design/COPY.md` Part 4 is generated from the code. | One set of strings, kept with the code that fills their slots, so B7 renders sentences and never builds them. Unchanged fingerprints mean answers saved under U2 still hide their questions. |
| Last due for "same party?" (U2b) | The questions loader reads the book (`loadShop`, then `partyAccount` as of the photo's day) only when a same-party question has exactly one match. The answer route skips it, because the sentences aren't shown there. The due is shown only when it is above zero, and it is `verified` when the page's "before" equals it. | The book is the only source of a due that agrees with the dues screen. Reading it for every page would add a full book read to every check-screen load, for a question most pages don't have. |
| Two-pass reading (U3, 2 Nov) | **Built, measured, left off.** `SCRIBA_TWO_PASS` reads a prompt-6 page as a layout call plus one call per block (≤ 7 calls, each counted by the rate limits). On the two flattened test pages, 4 runs each way: fields 86.1% vs single pass 87.9%, amounts 75.0% vs 80.6%, 2 extra lines vs 0, block kinds 8/8 vs 5/8, at $0.176 vs $0.071 a page and 29 s vs 16 s. It stays unset, in Vercel too. Scoring pairs lines by content (`align.ts`); the app's evaluations keep strict order. | Since C2 flattens the page, the remaining misreads are this writer's digit shapes, not pixels: sharp crops still turned ১ into ৯. A crop holds fewer of the writer's digits to compare, and a struck-out mark boxed as a block was read as an amount. Its one gain, the sales block kind, can be had in prompt 6 for one call. The code stays, off, for pages it wasn't measured on. |
| Company memo storage (U4, 2 Nov) | **A memo is a document**: one additive migration (`20261102180000_scriba_memos.sql`) adds `ledger_documents.kind` (`page` or `memo`) and `memo_for` (its page, same owner, deleted with it). It is uploaded like a page, registered with `memoFor`, and read through the same analyze route and `analyzeDocument`: one call with prompt `scriba-memo-1`, under the page's credit rules (cache, request id, one pending run, rate limits, checksum). Its reading is its run's `result`; it has no review rows and is never confirmed. Page lists filter `kind = 'page'`. **Written and tested in PGlite; not applied to the hosted project yet** (needs the user's go-ahead, before `track-engine` reaches `scriba-mvp`). | Every paid call is a run, and a run belongs to a document, so a memo must be one. The page's JSON can't hold it: page values are user-writable, and the memo's path and checksum must be server-attested. A memo isn't reviewed: a misread memo price is corrected on the page line, which is what gets confirmed, and the memo stays the model's reading as evidence. |
| Memo proposals (U4) | Code links a memo to the visit whose company or rep it names (else asks), pairs its lines with the visit's goods (sure only when each is the other's single best match), and checks its sums. A price is **proposed** only from a sure pair whose amount the model read with confidence, multiplies out, and sits on a memo whose lines agree with its total. Every unpriced good covered: one card with the memo's prices. After a discount: the memo's net total as one delivery line (U2's), only when its lines are exactly these goods. Anything less is offered as options. Goods on the memo but not the page are asked about (add or leave out), and so are page figures the memo gives differently (goods, before, payment). The `why` is ticked when code finds the page then comes to the due the memo prints. | The memo is another record of the same visit, so it can price goods, but it can be misread or be for someone else. Proposing only what three things support keeps one tap safe. Line prices after a discount add up to more than he owes, so only the net total is proposed then. The due tick is two records agreeing, worked out by code. |
| Answers and acceptance (B7, 2 Nov) | An answer accepts the lines its question was about (`acceptAnswered` in `src/components/check/ask-model.ts`) **only** when each has no blocker and every problem still on it is one he chose to keep (`acceptedFindings`). Checks that couldn't run (a balance waiting for a price) are accepted with it. Any other line goes through a quick-confirm card (lines with nothing to decide) or its own line card (lines with a problem no question covers). Lines an open or later question is about are left to that question. Confirmation is unchanged: `/confirm`, approval rules, server re-check. | Answers must never confirm money he hasn't seen. A "yes" to “Selim came from Pran, you owed ৳2,800 and paid ৳1,500” has shown him those two lines; it hasn't shown him a doubtful digit on another field, so that line still gets its own look. Keeping the existing acceptance model means the server needs no change and the old deck's guarantees hold. |
| Ask deck order (B7) | The page's own questions (the date) first, then block by block: its questions (consecutive price questions on one card), its problem lines, the quick confirm, its stamp; the page seal last. Done items drop out, so the deck is recomputed after every answer and the first item is the current card. Back returns to the block overview: an answered question isn't reopened in the deck (its lines can still be fixed from the quick confirm and the details page). | D5's design order (DESIGN_SPEC: “page questions, then block by block”); the engine lists the date last, and B7 renders, it doesn't reorder the engine. The server returns a fresh question set after each answer (follow-ups like `price:<row>` appear), so a fixed list would go stale. There is no undo for a saved answer, and inventing one would bypass the audit trail. |
| Ask deck screens (B7 part 2, 2 Nov) | A page whose reading has blocks (prompt 6) opens the ask deck (`AskSession`); a prompt-4 reading keeps the line deck. The server works the questions out when the page opens (`loadQuestionInput` with the review it already loaded). Cards are chosen by the answer's shape, not the question's kind: a proposed answer is one red button plus swipe right; two or three readings are big tiles with code's per-unit detail; other options are tiles; a value opens one sheet that holds the other options, the keypad or a text field, and the microphone. A heard answer only fills the field or picks an option; "Keep" saves it. A line fixed by hand asks the questions again (`GET /questions`). Classes are prefixed `as-` (P2 owns `ask-`). | The engine already decides what to ask; rendering by shape means a new question kind needs no new card. The text a mic hears is never saved without a tap, as in P1's fix sheet. Recomputing after a hand edit keeps every shown fingerprint current, so an answer is never refused as stale because of his own edit. |
| Prompt 6 stays opt-in (B7, 2 Nov) | U1 planned for B7 to make prompt 6 the default once the ask deck worked. The deck works, but the default stays prompt 4: prompt 6 runs only with `SCRIBA_PROMPT_VERSION=scriba-prompt-6`. The user decided this on 2 Nov. | Prompt 6 doesn't carry the Scriba-khata layout hint (`withLayout` applies to prompt 4 and 5 only) or the writer's personal notes (prompt 5 builds on prompt 4), so flipping now would quietly drop both on new readings. Port them to prompt 6 first (Track B), then flip `PROMPT_VERSION`. |
| Prompt 6 is the default; the writer's notes ride on it as prompt 7 (T6, 3 Nov) | Both were ported (prompt 7 = prompt 6 + prompt 5's writer rules, adapted to doubts and boxes; a blocks version of the khata layout), then `PROMPT_VERSION` became prompt 6. The user decided both on 3 Nov, after the measurement in `docs/sessions/T6.md`. Prompt 4 stays selectable, as `LINES_PROMPT_VERSION`. | Production already read with prompt 6 through a Vercel secret nobody can read back; the code now says what production does. On his five pages prompt 7 removed the ৩ → ৬ misread the notes named (0 against 3 and 5 per plain run) for 19% more per page. |
| The memo in the ask deck (U4 UI, 2 Nov) | A price slot starts with the price the company's memo proposes and says "from the memo". "Save the prices" sends the memo's option (`{ option: "memo:m1" }`) while the slot holds that price, else the typed value (`slotAnswer` in `src/components/check/ask-model.ts`). The memo shows as a crop of its photo round the lines the question names, or its letterhead when it names none. The check page sends the memo views (a signed photo URL, the lines' boxes, the printed due, `check.agrees`) with the questions: no new route. On a prices card with several slots, the tick is worked out as the slots change: with these prices the visit comes to the memo's printed due, else the memo's lines agree with its total. | The answer record should say where a price came from, and the memo's option also writes the memo's rate when the quantities match, which a typed value can't. Typing the memo's own number is the same answer, so it's recorded as the memo's. The tick follows the slots, so a retyped price never keeps a claim code no longer checks. The memo's photo is private like the page's, so it gets a signed URL the same way, in the same request. |
| Deployment (F1, 1 Nov) | Vercel project `scriba` (`scriba-one.vercel.app`, region `dub1`), deployed with the Vercel CLI from the local folder. `.vercelignore` is an allow-list (`src`, `public`, `package.json`, `bun.lock`, `next.config.ts`, `tsconfig.json`, `vercel.json`), and `vercel.json` pins `framework: nextjs`. ## Voice correction (built in P1; this was the plan)

Muse Voice Transcribe supports Bengali, and file transcription costs $0.18 per audio hour, so cost is not the issue. The work is:

1. Record in the browser and convert to mono 16-bit WAV (the endpoint accepts only WAV). Built at 24 kHz, the model's native rate per Meta's guide.
2. Add a server route that forwards the audio to `POST /v1/asr/transcribe` with `languageBias: ["Bengali"]`.
3. Put the transcript **into the field as text** for the user to save. It's never auto-applied and never sent to another model.
4. **The hard part:** people say numbers as words ("একশো আশি"). The deterministic number parser would need a Bangla number-word reader. It's testable, but it's new logic.

Estimate: one focused day. Build it only if the core flow, deployment and evaluation are finished by 2 Nov. If not, mention it as future work in the README.
